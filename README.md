# web-block-contracts

## What this is

The shared contracts of the Web Block services, in one place. It holds the gRPC protos under `proto/`, the JSON Schemas
of the events under `events/`, the action list of CheckAccess under `access/`, and the public REST APIs (v2, OpenAPI
3.1) under `openapi/`, one file per service. The layout follows the Notion page
"Web Block architecture", section 3.7. It holds no code. Each service copies what it needs from a pinned commit.

```text
proto/webblock/<service>/v1/*.proto
events/envelope.v1.schema.json
events/<service>/<event>.v1.schema.json
events/audit/audit_recorded.v1.schema.json   (one shape, sent by several services)
events/examples/valid/*.json
events/examples/invalid/*.json
access/actions.v1.json
access/actions.v1.schema.json
openapi/<service>-v2.yaml
puck/catalog-<version>.json                   (the web editor's blocks; generated, see "Editor component catalog")
```

## Status headers

The first line of each proto, and the start of each schema's `description`, gives its status. A data file such as
`access/actions.v1.json` has the status of its schema.

- `ACCEPTED`: taken word for word from Notion, or accepted word for word by the owner and the named consumer. Change
  it only by the rules of "How to ask for a change".
- `OWNED BY <service>`: the owner wrote it and keeps it.
- `DRAFT, proposed by <service>, waits for <owner>`: another service wrote it so work can start. The owner may change it
  or accept it. When the owner accepts it, the header becomes `ACCEPTED`.
- `DRAFT, proposed by <owner>, waits for <service>`: the owner wrote it and the named consumer or caller must
  agree. When that service agrees, the header becomes `ACCEPTED`.

## Event rules

- Every event body carries the envelope fields in snake_case: `schema_version`, `message_id`, `message_type`,
  `occurred_at`, `correlation_id`, `project_id`.
- Each event schema repeats the envelope fields, so one file checks one message. No schema allows extra properties.
- `message_type` is `<service>.<event>.v<n>`. The AMQP `type` equals it.
- A new field that a reader may ignore keeps the version. Any other change is a new file with the next version.
- Open point: `account.user_status_changed.v1` is about a user, not a project, so its draft has no `project_id`.
  The envelope schema requires `project_id`; Notion "Web Block architecture" 4.1 sends it "when there is one".
  The envelope's owners decide which rule holds.

## Examples

`events/examples/valid` holds at least one valid message for each event. Each file in `events/examples/invalid` differs
from one valid file in exactly one property. Its name says the rule it breaks, for example
`source-published-39-char-sha.json`. Every invalid example fails its schema alone, without any other check.

## Editor component catalog

`puck/catalog-<version>.json` describes the blocks of a website page as the web editor saves them (Puck): each block's
props with their JSON Schema (draft 2020-12), whether a prop is required or nullable, the page rules (block limit,
blocks per type, the Footer last), and what WebBlock AI may do (`ai`: `edit` or `none`, with a `flag` saying why:
`media`, `products`, `setting`, or since 0.2.0 `owner`; `aiOperations`; `addDefaults`). Since 0.2.0 each prop also
has a `note` (what it is and how the site shows it) and, on block props, the `default` a newly dropped block holds.
Since 0.3.0 blocks nest: containers list their `slots`, every component says whether it is `topLevelOnly`, `page`
gains `topLevelLimit`, `maxDepth`, `uniqueBlockIds`, `anchors` and a `notes` line per rule, and two new top-level keys
describe the rich text tree (`richText`, with its JSON Schema) and where every picture's alt text comes from
(`images`). The 0.3.0 file also states which rules are strict (`page.strictSince`, `since` on every 0.3.0 block,
prop and slot), the block id rule (`page.blockId`), the document's shape (`page.document`) and conformance strings for
its patterns (`patterns`). `version` is the `componentCatalogVersion` Project stores with each page.

- OWNED BY webui. It is generated from the editor's own save check by `pnpm puck:catalog --contracts <checkout>` in
  webblock-web-ui (src/features/editor/catalog.ts), never edited by hand. `--check` says whether a file still matches.
- A released version never changes. A change to a block or a prop is a new file with the next version; the exporter
  refuses to rewrite a released one.
- Readers: ai_codegen (the assistant's allowed edits and its prompt) and project (the page check on save). They pin a
  commit like any other file here.
- The editor also serves it live for agents and tooling: `GET /api/puck/catalog`, and an MCP server at
  `POST /api/puck/mcp` (read-only tools `list_components`, `get_component_schema`, `get_root_schema`, `get_catalog`).
  Services read the pinned file, never the live routes.

### Versions

| Version | Blocks | Page rules |
|---|---|---|
| 0.1.0 | Hero, Text, ProductCards, AllProducts, About, VisitUs, Footer | 12 blocks a page, the Footer last |
| 0.2.0 | 0.1.0's seven, unchanged, plus Testimonials, FAQ, Gallery, CallToAction, Services, Stats (content only: no products, no new data, images through the existing media upload) | 16 blocks a page, the Footer last |
| 0.3.0 (DRAFT for review) | 0.2.0's thirteen, unchanged (only new optional alt props on Hero, Text and About), plus the containers Section, Columns, Grid, Card and the design blocks Heading, RichText, Image, Buttons, Icon, Spacer, Divider, ImageBanner, LogoStrip, Quote, Video, Map; root gains optional `seoTitle`, `seoDescription` | 40 blocks a page at every depth, 16 at the top level, depth 3, Hero and Footer top level only, the Footer last, live-data blocks (ProductCards, AllProducts, About, VisitUs) in no slot, block ids unique across the tree, `zones` empty; 0.3.0 blocks and props strict; no WhatsApp links (`page.links.blockedHosts`); the `telegram` CtaAction and root `telegramUrl`; ProductCards and AllProducts choose which catalog products they show (`source`, `category`, `productIds`, AllProducts `defaultCategory`), and Project checks the ids |

- **A newer 0.x only adds.** Every block, prop and value rule of the older version is the same in the newer one,
  and its page rules are the same or looser. So every page valid under 0.1.0 is valid under 0.2.0. A version that
  breaks this needs its own migration plan, and must not be numbered 1.0.0: AI Codegen already uses "1.0.0" for its
  own generated-site catalog.
- **Version order** is numeric major.minor.patch ("0.10.0" is newer than "0.9.0"). A version a reader can't parse
  or doesn't pin is refused.
- **0.2.0's AI policy:**
  - WebBlock AI may add Text, FAQ, CallToAction and Services, starting from `addDefaults`.
  - It never invents business facts: delivery areas or times, payment methods, prices, opening hours, services
    offered, numbers. FAQ answers and Services cards hold only facts from the owner's prompt or already on the
    page; where the owner gave none, the assistant keeps a placeholder that asks for them (as `addDefaults` do).
  - It edits the wording of Testimonials, Gallery and Stats (heading, eyebrow) and may move or remove them, but
    never adds them.
  - `Testimonials.items` and `Stats.items` are `owner` facts: real customers' words and the business's own
    numbers, which the assistant never writes or changes. Their `default`s are plain placeholders ("Replace this
    with words a real customer said about you.", "00 / Your first number"), never values that pass for real.
  - `Gallery.images` is `media`.
  - Known 0.1.0 leftover: `About.stats` (small facts such as "10+ years") stays AI-editable, because changing an
    old block's policy would not be additive. The assistant should still not invent numbers there.
- **How a page moves from 0.1.0 to 0.2.0: on its next save from a 0.2.0 client.**
  1. The page saves (`PUT /api/project/v2/projects/{projectId}/page` from the editor, and
     `PUT /internal/v1/projects/{projectId}/page/draft` from AI Codegen) carry an optional `componentCatalogVersion`:
     the catalog the client built the page with.
  2. Without it, Project checks the page against the project's stored version, as today, so older clients are
     unchanged.
  3. With it, Project checks the page against that version. A version Project doesn't pin is
     `400 VALIDATION_FAILED` (field `componentCatalogVersion`). So is one older than the stored version, because
     a page never moves down.
  4. On success, Project stores the sent version as the project's `componentCatalogVersion`.
  5. The 0.2.0 editor always sends `"0.2.0"`, so an old page moves up the first time the owner saves it, unchanged
     (a 0.1.0 page is a valid 0.2.0 page).
  6. AI Codegen sends the version of the catalog it built its change set with.
  7. A restore (PATCH) keeps the stored version: an older published tree is valid under the newer catalog.
- **Rollout order.** `componentCatalogVersion` is optional for Project's callers, but today's Project refuses
  unknown body properties, so a client must not send it before Project accepts it. Ship in this order:
  1. AI Codegen's catalog loader accepts the flag value `owner` (it reads `flag` as a closed list), and its site
     template renders the six new blocks (a block type the site doesn't know must not be dropped silently);
  2. Project pins 0.2.0 and accepts the field on both page saves;
  3. then the 0.2.0 web editor and AI Codegen sending the field.
- **Pages never saved again stay 0.1.0** and keep working: they hold only 0.1.0 blocks, which every reader of
  0.2.0 still knows.
- **New projects:** Project creates them at their template's `componentCatalogVersion` (templates.json); a template
  moves up only once the editor of that version is live.
- **The live site:** the site template renders every block of the newest version (unknown types are never on a
  saved page, since Project refuses them). The template needs no per-version branch.

#### 0.3.0: containers and design blocks (DRAFT for review)

- **Additive.** 0.2.0's thirteen blocks keep every prop, value rule, `default`, `note`, `maxPerPage`, `aiOperations`
  and `addDefaults` byte for byte; the root's 0.2.0 props too. New on old blocks are only optional props (`required:
  false`): `Hero.imageAlt`, `Text.imageAlt`, `About.imageAlt`, `About.secondImageAlt`, root `seoTitle`,
  `seoDescription` and `telegramUrl`, and the "Products to show" props of ProductCards and AllProducts (`source`,
  `category`, `productIds`, AllProducts `defaultCategory`; see "Products to show (data binding)" below). The web UI's
  tests compare 0.3.0 with this repository's 0.2.0 file.
- **Strict from 0.3.0.** `page.strictSince` is `"0.3.0"`, and every block, prop and slot added in 0.3.0 carries
  `"since": "0.3.0"` (the new blocks, all their props and slots, and the props above). For those:
  - Project refuses with `400 VALIDATION_FAILED` (code `VALUE_INVALID`, field as in "Refusals in 0.3.0" below) any
    value that fails ANY keyword of its schema: `pattern`, `minLength`/`maxLength`, `minItems`/`maxItems`, `enum`,
    `const`, `type`, `uniqueItems`, `additionalProperties`. It also refuses an unknown prop or item key on a 0.3.0
    block (the 0.3.0 item objects, `Buttons.items[]` and `LogoStrip.logos[]`, are `additionalProperties: false`; so is
    every rich text node).
  - No stored page can break these rules: nothing held a 0.3.0 block or prop before.
  - The log-only leniency of 14 November (keywords logged, unknown props let through) stays only for props without
    `since` (0.1.0 and 0.2.0), whose stored values are older than the editor's checks.
  - AI Codegen checks the same before it proposes a change set, so the assistant never offers a value Project refuses.
- **Refusals in 0.3.0** (the coordinator's decision of 15 November 2026). Project refuses a page checked against 0.3.0
  with `400 VALIDATION_FAILED`, and every entry of `errors` is spelled one way, extending what its catalog check
  answers today (`content[0].Hero.align`, `VALUE_INVALID`). `field` walks the tree: `content[i].<Type>.<prop>` for a
  top-level block, one `.<slot>[j].<Type>` more per level for a nested one
  (`content[i].<Type>.<slot>[j].<Type>.<prop>`), a list item's index after its prop, and `root.<prop>` for the page's
  settings. A structural refusal names the block or slot concerned the same way, never `puckTree` plus a JSON pointer.
  `code` is `VALUE_INVALID` for a value (any schema keyword or pattern, the rich text rules, a required alt, a link
  rule or blocked host, a `productIds` entry that is not a product of this website) and `PUCK_TREE_INVALID` for the
  structure (depth, a slot's `allow`/`disallow`, `minItems`/`maxItems` and `activeWhen`, `topLevelOnly` and the Footer
  last, the budgets, a repeated block id, `zones`). For example: `content[3].ProductCards.productIds[1]`
  `VALUE_INVALID` (another website's product), `content[2].Columns.column1[0].Buttons.items[1].link` `VALUE_INVALID`
  (`https://wa.me/85512345678`), and `content[1].Section.content[0].ProductCards` `PUCK_TREE_INVALID` (live data in a
  slot).
- **Containers and slots.** Section, Columns, Grid and Card hold blocks in slot props (Puck slots): each slot is a
  prop whose value is a list of blocks, `{type, props}` exactly as at the top level. Slot props are listed under the
  component's `slots`, not under `props`. Each slot has:
  - `allow`: a list of block types, or `"any"`: every type whose `topLevelOnly` is false, minus `disallow`;
  - `minItems` and `maxItems` (Section 0–12, Columns 0–6 per column, Grid 0–12, Card 0–6);
  - for Columns, `activeWhen`: `column1` and `column2` always, `column3` with a three- or four-part `ratio`, `column4`
    only with `25-25-25-25`. A slot that is not in use must be empty; the save check refuses blocks in it.
  - What fits: a Section takes any block but Hero, Footer, Section and the live-data blocks; a column takes the small
    blocks (Heading, RichText, Text, Image, Buttons, Icon, Spacer, Divider, Quote), Video, Map and Card; a Grid takes
    Card, Image, Quote, Icon, Heading, RichText, Text, Buttons and Video; a Card takes the small blocks.
  - **Live data stays at the top level** (DEFAULT pending coordinator). ProductCards, AllProducts, About and VisitUs
    show the Owner Portal's products, categories and business facts, which both renderers fill in only at the top
    level. No slot takes them (they are in Section's `disallow`; the other slots' lists leave them out), so no
    renderer changes. Opening them to slots later is additive.
- **Depth and budgets.** A top-level block is depth 1, a block in its slot depth 2, one more level depth 3;
  `page.maxDepth` is 3, so a container at depth 3 (a Card in Columns in a Section) stays empty. `page.blockLimit` is
  40 and counts blocks at every depth; `page.topLevelLimit` is 16 (0.2.0's `blockLimit`). Each `maxPerPage` counts
  nested blocks too (five Text blocks, wherever they sit). For a flat 0.1.0 or 0.2.0 page every count is what it was.
- **topLevelOnly.** Hero and Footer are never inside a container; the Footer is still the last top-level block.
- **Block ids.** `page.blockId` gives the id rule: `props.id`, a string of 1–100 characters (`blockIdProp` stays for
  older readers). Every id is unique across the whole tree, slots included. With `zones` empty (below), this is one of
  the two rules new for old pages too. The editor (Puck) and the assistant's ADD always made unique ids, so no saved
  page should break; Project can confirm both on its stored drafts before it pins 0.3.0. AI Codegen's ADD ids keep to
  the same 1–100.
- **The document.** `page.document`: a page holds `root`, `content` and `zones`, and `zones` is absent or `{}`.
  Blocks nest through slots only; no block has a DropZone. No valid 0.1.0 or 0.2.0 page breaks: Puck writes
  `zones: {}`. Project's 0.3.0 check gives `zones` `maxProperties: 0`.
- **Anchors.** A Section's `anchorId` is empty or 2–40 small letters, digits and `-` starting with a letter. When set,
  it is unique on the page and never one of `page.anchors.reserved`: `top`, `shop`, `visit`, `about`, `all-products`,
  the site's own in-page link targets. It is `setting` for the assistant: other pages and posts may link to it.
  - Every other id the site emits must contain a character the anchorId pattern can't produce. The later build
    renames three that don't yet, in the web UI's designs and AI Codegen's site template: `warm-bold-mobile-nav`,
    `jackets-badge-circle` and `site-contact-title` (to, for example, `warm_bold_mobile_nav`).
- **Rich text** (`RichText.body`) is a restricted node tree in the TipTap/ProseMirror JSON shape, never HTML.
  - Nodes: `doc`, `paragraph`, `heading` (`attrs.level` 2–4), `bulletList`, `orderedList`, `listItem` (paragraphs
    only, so no nested lists), `text`. Marks: `bold`, `italic`, `link` (`attrs.href` is a link target, below).
  - Objects are strict (`additionalProperties: false`): any other node, mark or key (`class`, `style`, `target`,
    `onclick`) is refused, not dropped. Alternatives are `anyOf` (each branch has its own `type` const); the file uses
    no `oneOf`.
  - `richText.schema` is the full JSON Schema, inline with no `$ref`, and the same as `RichText.body`'s.
  - Two rules a JSON Schema can't hold, checked on the page by every reader:
    - `richText.maxTextLength` (2000), with `richText.lengthUnit` `"utf16"`: the sum, over every text node of one
      body (paragraphs, headings and list items), of its length in UTF-16 code units: JavaScript `length`, Java
      `String.length()`, Python `len(s.encode("utf-16-le")) // 2`. JSON Schema's own `maxLength` counts code points,
      so it is no substitute. One run may hold the whole 2000, because ProseMirror merges neighbouring runs with the
      same marks: merging must never turn a valid tree invalid.
    - `richText.marksOncePerRun`: a run carries each mark type at most once (never two links, never bold twice;
      ProseMirror refuses such a run). The schema's `uniqueItems` on `marks` only catches two equal marks.
  - `richText.examples` are conformance trees with `valid` and the `rule` that refuses an invalid one: a 1500-character
    paragraph, two same-mark runs, emoji at 2000 and 2001 units, repeated marks, a `data:` link, a style key, an html
    node.
- **Patterns.** The value rules new in 0.3.0 are JSON Schema `pattern`s built from ASCII classes only (no `\s`, `\d`,
  `\w` or negated class, no lookaround, no flags), so their result does not depend on the engine.
  - **A pattern matches the whole string under ECMA-262 rules** (`$` is the end of input). Python readers use
    `re.fullmatch` (not `search` or `match`); Java readers use `Matcher.matches()` or networknt's ECMA-262 regex (never
    `find()`).
  - **Conformance strings.** The top-level `patterns` lists each pattern with the props using it, and `accept` and
    `refuse` strings every reader must agree on. The refuse lists include NBSP, U+2028, ZWSP, RLO, NUL, a trailing
    newline, Arabic-Indic digits and a Cyrillic look-alike. The file writes invisible characters as `\u` escapes. The
    web UI checks them in JavaScript (with and without the `u` flag), Python `re.fullmatch` and Java
    `Matcher.matches()`.
  - **Lengths** in the editor count UTF-16 code units. A reader whose `maxLength` counts code points is looser for
    emoji; AI Codegen counts UTF-16 already.
  - **Links** (`Buttons.items[].link`, `ImageBanner.buttonLink`, a rich text link's `href`): a `CtaAction` target
    (`shop`, `visit`, `call`, `email`, `directions`, and since 0.3.0 `telegram`) or an `https://` address. The host is
    dot-separated labels of letters, digits and hyphens whose last label starts with a letter (so no IP literal and no
    `localhost`), with an optional port. The path, query and fragment hold URL characters only. No `javascript:`,
    `data:`, `http:`, `mailto:`, relative paths, `#anchors` or `user:password@`, and no blocked host (below). The 0.1.0
    and 0.2.0 buttons keep their `CtaAction` only.
  - **No WhatsApp** (the owner's decision of 15 November 2026). `page.links.blockedHosts` is `wa.me`, `whatsapp.com`,
    `whatsapp.net` and `wa.link`, with `hostMatch: "suffix"`: a link is refused when its host, lower-cased and without
    a trailing dot, equals an entry or ends in `.` + an entry.
    - The host is what a WHATWG URL parser reads (JavaScript `new URL(v).hostname`, Python `urlsplit(v).hostname`,
      Java `URI.getHost()`). For a 0.3.0 link it is simply the text between `https://` and the first `:`, `/`, `?` or
      `#`, since the link pattern allows no userinfo, backslash or percent sign there.
    - Every reader enforces it on `page.links.appliesTo`: `Buttons.items[].link`, `ImageBanner.buttonLink`, rich text
      hrefs and `root.telegramUrl`. The editor's save check also enforces it on the 0.2.0 social links
      (`page.links.editorAlsoChecks`: `root.facebookUrl`, `root.instagramUrl`), so a page holding such a link no
      longer saves from the 0.3.0 editor until the link is changed.
    - Refused: `https://wa.me/85512345678`, `https://WA.ME/85512345678`,
      `https://api.whatsapp.com/send?phone=85512345678&text=Hello`, `https://chat.whatsapp.com/x`,
      `https://www.whatsapp.com/`, `https://web.whatsapp.net/x`, `https://wa.link/abc123`. They match the link
      pattern, so only the host rule refuses them (`page.links.examples.blocked`, `patterns.link.blockedByHost`).
    - Not blocked (`page.links.examples.allowed`): `https://t.me/riversideroasters`, `https://notwa.me/x`,
      `https://mywhatsapp.com/x`, `https://whatsapp.com.example.com/x`, `https://wa.linked.example.com/x`.

    brackets, parentheses, semicolons or spaces. The 0.1.0 and 0.2.0 picture props keep their own pattern: versions

    - The site takes the YouTube id (the 11 characters after `watch?v=`, `embed/`, `shorts/`, `live/` or `youtu.be/`)
      or the Vimeo id (the digits after `vimeo.com/` or `video/`, and the hash from `/<hash>` or `h=`).

  - **Nested operations** (accepted by ai_codegen with its changes of 15 November; specified in
    `openapi/ai-codegen-v2.yaml`, `ChangeItemPosition`):
    - ADD and MOVE carry `position {parentId, slot, index}`, where `parentId: null` is the top level. A position with
      only `{index}` is still read as top level. An ADD without an `index` goes at the end of its list, as today.
    - `componentId` (and an "@" `BlockRef`) finds a block at any depth, since ids are unique across the tree.
    - Each item is checked structurally as it is applied: the parent exists, `slot` is one of the parent's `slots`,
      and `index` is at most the target list's length.
    - The catalog's rules are checked once, on the FINAL tree of the change set, not after each item: `allow`/
      `disallow`, `activeWhen`, `minItems`/`maxItems`, `maxDepth`, `topLevelOnly`, both budgets, unique ids, anchors
      and every value rule. A change set that breaks one is refused whole. So a wrap at the 16 top-level limit works:
      ADD the Section, then MOVE the blocks into it.
    - Slot props never appear in an UPDATE's `propsPatch`: a container's children change only through ADD, MOVE and
      REMOVE. On ADD a slot key may only be `[]`, as the containers' `addDefaults` have it.
    - MOVE's `index` counts in the target list after the block has been taken out of its old place, as the top-level
      MOVE does today. A MOVE into the moved block's own subtree is refused.
    - Turning off a Columns slot that still holds blocks (a three-part `ratio` changed to a two-part one with
      `column3` filled) fails the final-tree check (`activeWhen`), for the model and in the editor alike: MOVE or
      REMOVE those blocks first. The editor says so when the owner picks such a ratio; it never hides or drops them.
    - REMOVE of a container removes its whole subtree.
    - There is no WRAP or UNWRAP: wrap = ADD the container, then MOVE the blocks into its slot; unwrap = MOVE the
      blocks out, then REMOVE the container. `aiOperations` keeps the same four values.
    - Refs are the model's only. In its output an ADD may name the block it adds with a `ref` (`^[a-z][a-z0-9-]{0,39}$`)
      that later items' `position.parentId` may use. A ref may not equal an existing block id or another ref of the
      set, and may be used only after its own ADD; otherwise the change set is refused. AI Codegen generates the ADD's
      id when the change is proposed and resolves the refs then, so stored and returned change sets carry real ids and
      never a ref.

##### Products to show (data binding)

Part of the 0.3.0 draft: the owner's design of 15 November 2026, with the coordinator's decisions of the same day
(points 1–6 below). A product block says WHICH of the website's catalog products it shows, and the editor reads the
Owner Portal's catalog to fill that choice.

- **The props.** ProductCards and AllProducts gain three optional props, AllProducts a fourth. Like every 0.3.0 prop on
  an older block they are `required: false`, carry `"since": "0.3.0"` and are strict (every keyword enforced, `null`
  refused). Unlike the alt props they have a `default`, which is also what a missing prop means: a page saved before
  0.3.0 shows what it showed, and a newly dropped block holds the defaults.
  - `source`, "Products to show": `all`, `category` or `picked`; default `all`; `ai: edit`.
    - `all`: the whole catalog, today's behaviour.
    - `category`: only the products of `category`.
    - `picked`: only the products in `productIds`, in that order.
  - `category`: a string of at most 40 characters (as long as a product's own `category`); default `""`; `ai: edit`.
    Used only with `source: "category"`, ignored otherwise. It must name a category of the website's catalog: the web
    UI and AI Codegen check that against the catalog; Project only logs an unknown one (a category may also be deleted
    after the save).
  - `productIds`: at most 12 (`maxItems`) product ids with no repeats (`uniqueItems`); default `[]`; `ai: none`, flag
    `owner` (the assistant never invents or picks products). The owner's order is the display order. Used only with
    `source: "picked"`; kept but ignored otherwise, so going back to `picked` restores the picks.
    - Each id matches `patterns.productId`, `^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`: Project's
      `Product.id` (the shared catalog's `product_id`, which the site template reads) in its lowercase form, so a
      product has one spelling and `uniqueItems` finds a repeat.
    - Its accept and refuse strings are checked like the other patterns. The refuse list has upper case, no hyphens,
      braces, `urn:uuid:`, a product name, NBSP, U+2028, ZWSP, RLO, NUL, a trailing newline, Arabic-Indic digits and a
      Cyrillic look-alike.
  - AllProducts only: `defaultCategory`, a string of at most 40 characters; default `""`, the All tab; `ai: edit`. It
    is the tab the block opens on, checked like `category`. An unknown one opens on the All tab.

     The editor writes only the choice. It never fills `products` or `categories` from the catalog (today it already
     only shows the catalog on the canvas) and never clears them: what a page holds (the template's sample products)
     stays as stored. Older readers keep what they had.
     - Note: the platform never seeds template products, so AI Codegen's first-deploy seed of an empty catalog from

  5. **How a category name matches, and what "hidden" means.** Decided 15 Nov: names match ignoring case (Project's

  6. **The refusal's field spelling and code.** Decided 15 Nov: one spelling for every 0.3.0 refusal, "Refusals in

## WebBlock AI skills

`assistant/skills/<name>.md` are the WebBlock AI chat's skills, one file per "/" command: what the command does for
the owner (in English and Khmer), when the router picks it, its rules, and worked examples. `assistant/rules.md` holds
the rules every skill follows. `assistant/skills-<version>.json` is the index built from them by
`node assistant/build-skills.mjs` (`--check` compares), never edited by hand.

- OWNED BY webui (the files and the index), reviewed by the AWS config session. Readers: ai_codegen (the router,
  the prompts, the evals) and the web UI (the "/" menu, `/help`, the chat's empty state, the reply's skill tag, and
  the MCP server's prompts). They pin the index file by commit, like the editor catalog. Neither keeps a copy of the
  wording: a command's description is shown from `summary` / `summary_km` everywhere.
- **Frontmatter** (YAML where every value is one line of JSON):
  - `name` (the file name; `command` is `/<name>`), `aliases`, `title`, `skill` (shown as "Used: <skill>"),
    `group` (`design`, `content`, `utility`) and `order` (the menu order in the group);
  - `args`: `null` or `{"name", "hint", "hint_km", "required"}`, e.g. `/translate <language>`;
  - `blocks` (block types it suits, `*` for any) and `triggers` (English and Khmer words for the router's fallback);
  - `mode`: `change` (proposes operations), `reply` (answers only, no operations) or `client` (answered by the chat
    itself, never sent: `/help`); `maxTokens` 300–800 (null for client);
  - `summary` (at most 80 characters) and `example`, with `summary_km` and `example_km` in Khmer, and
    `km_reviewed`: false until a person has checked the Khmer.
- **Body:** `## Rules` (the skill's own rules) and `## Examples`: JSON blocks with `message`, optional `refs` and
  `page`, and the model's `output` (`reply` and `operations`, as AI Codegen's assistant answers). The build checks
  every example against the editor catalog named in the index: props exist, values keep their rules, `ai: none`
  props are never written, ADD only where `aiOperations` allows it and complete, and with refs only those blocks.
- **Routing (AI Codegen):** `SendAiMessage.command` picks the skill by `name`; else the "@" blocks' types (`blocks`);
  else a keyword match on `triggers`. At most two skills join the base prompt; the reply's `AiMessage.skill` names
  the one used.
- **Labels:** `assistant/labels.json` holds the few words around the descriptions where the chat lists them (the
  mode labels "Changes your page" / "Only answers", "e.g.", the list's heading and hint, "Used:"), in English and
  Khmer; the build copies them into the index's `labels`, so the UI keeps no copy of that wording either.
- **Placeholders:** the index's `placeholders` lists the editor's starter texts (`{prop, text}`), taken by the build
  from the catalog's `default` values for the props in `PLACEHOLDER_PROPS` (build-skills.mjs). /check and /fill use
  that list; the web editor's pre-Deploy warning checks the same props. A listed prop without a starter text in the
  catalog, or a skill rule that quotes a starter text, fails the build.
  - **Rich text starter texts (catalog 0.3.0).** For a prop whose default is a rich text doc (`RichText.body`), the
    index lists one `{prop: "RichText.body", text}` per text run of the default. A block still holds starter text when
    any text run in its tree equals a listed text. This waits for the skills index built on catalog 0.3.0 (rollout
    step 0). `build-skills.mjs` (which keeps only string defaults today) and the web UI's `block-defaults.ts`
    (`starterTexts`, `placeholderBlocks`) walk the doc's runs in the same change that moves the 0.3.0 starter texts
    into `PLACEHOLDER_PROPS`: `Heading.text`, `RichText.body`, `ImageBanner.heading`, `ImageBanner.body`,
    `Quote.quote` and `Quote.author`.
- A released version never changes; new or changed skills are the next version.

## How to ask for a change

Any team may ask any service for something here, Project and Provisioning included.

1. Write a branch with a new DRAFT file, or a change to another service's file, and open a merge request in this
   repository. A new file starts with `DRAFT, proposed by <your service>, waits for <owner>`, follows the naming and
   event rules above, and passes the checks (valid and invalid examples for an event, `protoc` for a proto). Add or
   change its row in "What each service needs from the others", with your own spec IDs.
2. The owning service reviews it. It accepts it word for word, and the header becomes `ACCEPTED`; or it answers in the
   merge request with what must change. Only the owner changes its own files.
3. A breaking change is a new file with the next version (`.v2`, package `v2`) next to the old one. An accepted `.v1`
   is never edited, except to add a field a reader may ignore.
4. A service pins a full commit SHA and moves it on purpose (see "How a service pins it").

## Action list

`access/actions.v1.json` names every action that `AccessService/CheckAccess` accepts. Each action has `name`, `write`
and `admin_allowed`. `write` is true when the action changes state and false for a get or list action. `admin_allowed`
is true when a caller may let an admin through without asking Project. `access/actions.v1.schema.json` checks the file.
Names are unique.

## How a service pins it

A service never reads this repository live. It keeps the full commit SHA it uses in its own `contracts.lock` file. A
script copies the files it needs from `events/`, `proto/` and `access/` at that commit and generates code from the
protos. A check fails when the copy differs from the pinned commit. To take a change, a service moves its SHA and runs
its sync again, in one reviewed change.
